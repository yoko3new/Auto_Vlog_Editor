## Codex 与 Replit 怎样协作和部署

<a id="s18-1"></a>

### 推荐开发方式

**继续以本地开发为主：本地编辑和调试 → GitHub 保存代码 → Replit 拉取、运行和正式发布。** 使用 Replit 不要求把日常编码全部迁到浏览器；本项目先由 Replit 承担云端验证和上线，前后端作为同一个应用发布。

用一个 GitHub 仓库作为代码交接点：Codex 在本地改代码、验证并提交；Replit 导入同一仓库，拉取更新、运行和预览。Replit 中产生的改动也提交并推送，再由本地拉取。Git 同步需要显式操作，不是两边文件自动实时同步。[Replit 导入说明](https://docs.replit.com/build/import-from-providers)、[版本控制说明](https://docs.replit.com/learn/projects-and-artifacts/version-control)

建议让 Codex 重点做接口、时间线、渲染与错误排查，让 Replit Agent 帮忙搭页面和检查运行环境；这是分工建议，两者都能参与前后端。每次给任务明确[开工约定与单一负责人](collaboration.md#s13-1)的文件范围、分支和验收标准，避免两个 Agent 同时重写相同文件。正式发布由 A 使用合并后的 main 执行。

本方案不依赖专门的 Codex–Replit 连接器。API 密钥在 Replit Secrets 单独配置，不会因为导入 GitHub 仓库就自动齐备。

<a id="s18-2"></a>

### 开工验证：先确认 Replit 能跑通，再接 AI

**目的：证明真实素材能在 Replit 正式环境完成“上传 → 后台剪辑 → 保存 → 播放下载”。** 先用固定剪辑计划隔离平台问题，通过后再接 AI、完善杂志风和三类修改。这些是同一个 MVP 的开工步骤，不另建一套验证应用，也不额外增加 36 小时之外的工作阶段。

当前状态：以下关卡均为**未验证**。已有 JSON 检查不代表 FFmpeg 或 Replit 实测成功。

**准备最小样本和页面**

- 三段各不少于 3 秒的 1080p SDR 视频，另备一首足够长的可用 BGM 和实际字体文件。随附 JSON 中的素材路径只是示例，没有包含真实媒体。
- 第一轮按固定顺序各取 3 秒，原声静音，加入固定标题、轻微暖色和 BGM；硬切输出 9 秒、1280×720、30 fps、H.264/AAC MP4。
- 页面只需上传、生成、真实处理状态、播放器和下载；项目链接包含 `project_id`，方便重新打开后恢复。
- 后端登记真实素材 ID，程序把手工 `edit_plan.json` 编译成符合[JSON 数据契约：MVP 可用，V2/V3 可扩展](reference/timeline.md#s6)的 `timeline.json`，不要直接使用占位资源引用。九秒样本使用 `duration_policy.mode=natural`、`target_seconds=null`、`tolerance_frames=0`，总长 270 帧；这是开发验证样本，正式 MVP 首次生成仍默认 30 秒，也不向用户增加九秒选项。

**关卡 A：环境能运行（0–2 小时）**

| 检查项 | 具体操作 | 通过标准 |
| --- | --- | --- |
| 本地到云端的代码交接 | 建立 `frontend/`、`api/`、`core/` 和 `/api/health`；推送 GitHub 后导入 Replit，再同步一次页面文字修改 | 同一份代码能启动，能确认拉到的是最新提交 |
| 视频处理依赖 | 检查 Node、Python、FFmpeg、ffprobe、字体；用真实素材运行小视频合成命令 | 实际输出含标题、调色和音乐的有效 MP4；安装成功或打印版本号不能代替成片 |
| 发布配置 | 查看可用部署类型、CPU、内存和费用；构建前端，由 FastAPI 提供网页、`/api` 和媒体接口，再发布最小骨架 | 正式网址的 `/api/health` 可访问；记录构建/启动命令、端口和机器配置 |

此时不要求漂亮界面或 AI。字幕与溶解依赖仍留到对应 V2/V3 阶段另验。

**关卡 B：正式链接完成最小闭环（2–6 小时，先做）**

开发预览通过后，在正式发布的网址重新测试下面各项。Preview 与正式部署是两个环境，页面改动需要重新发布；不能拿 Preview 的测试结果填正式环境的验收记录。[Replit 发布说明](https://docs.replit.com/build/publish-your-app)

| 检查项 | 具体操作 | 通过标准 |
| --- | --- | --- |
| 上传与后台处理 | 从正式网页上传三段素材并点击生成，使用手工计划 | 接口及时返回 `job_id`；后端真实渲染，轮询显示真实阶段，网页仍能响应 |
| 离开页面后继续 | 确认任务进入渲染后关闭页面，再打开相同项目链接 | 服务仍运行时，任务继续处理；重新打开可找回状态和结果 |
| 播放与下载 | 在网页播放、拖动进度条，再下载到电脑播放 | 画面、标题、暖色和音乐正确；媒体接口支持拖动播放，下载文件可用 |
| 持久保存与恢复 | 确认原素材、项目/版本 JSON 和成片已写入 App Storage；在成功后重启正式服务或重新部署，回到同一项目链接 | 能恢复素材记录和成功版本，重新播放、下载；确认恢复读到了 App Storage 文件，而非仅依赖旧进程内存或本地缓存 |
| 错误与队列恢复 | 提交无效文件；另在测试模式让一个已入队渲染任务失败，然后提交正常任务 | 无效文件有提示；后台失败被记录并释放队列，后续正常任务能完成，旧成片仍可播放 |

App Storage 用来持久保存文件，本地目录只作处理时的临时工作区，具体保存顺序见[需不需要数据库：单实例演示先不用，但要持久存储](architecture.md#s11)。[App Storage 文档](https://docs.replit.com/features/data-and-storage/object-storage)

**关闭页面和服务重启是两种情况。** 关闭页面时服务还在运行，后台任务应继续；重启会终止正在执行的任务，MVP 只要求将其标为 `interrupted` 并允许重试，同时保留此前成功版本，不承诺断点续跑。刷新页面不能代替重启测试；需另外在渲染中重启一次，确认不会永远显示“处理中”。

**关卡 C：实际素材量能稳定处理（2–6 小时，B 通过后做）**

输入 10–15 段、总长不超过 3 分钟的合规素材，包含足够的可用区间；按手工计划生成约 30 秒、720p 视频，包含标题、暖色和 BGM。连续串行执行三次完整渲染，不复用旧成片冒充重新生成。记录首次处理与缓存复用的差别。

分别记录上传、读取/规范化、时间线计算、渲染、保存到可播放的耗时，以及 CPU/内存情况、素材总字节数和机器规格。三次均应实际完成，画面声音正常，没有内存不足、进程退出或任务卡死；据此确定当前部署可接受的上传体积上限。无法读取某项指标时标为“未采集”，不要填估算值。

九秒小样通过只证明基本流程可行。关卡 C 才检查接近 MVP 的处理负载；此时没有 AI，因此耗时不能当成完整 AI 生成速度。90 秒仍是优化目标，稳定完成是这一关的首要标准。

**记录与失败处理**

每项记录“通过 / 失败 / 未验证”，附测试时间、代码提交、正式环境配置、`project_id` / `job_id`、耗时、成片或日志位置。环境、渲染配置或存储实现改变后，重测受影响的关卡；接入 AI 后按[按阶段验收、性能和风险](acceptance.md#s15)再验收完整 MVP。

| 现象 | 优先排查 | 对后续工作的影响 |
| --- | --- | --- |
| 本地能跑，Replit 不能启动 | 依赖、字体路径、构建与启动命令、端口 | 先修环境，不继续叠加 AI |
| Preview 成功，正式链接失败 | 发布版本、依赖、环境变量、App Storage 访问配置 | 正式环境仍算未通过 |
| 关闭页面后任务丢失，或一个失败卡住全部任务 | 任务是否独立于请求执行、状态是否写入、异常是否释放队列 | 修好后台生命周期再继续 |
| 重启后旧成片找不到 | 文件是否真正持久保存，项目指针和读取逻辑是否正确 | 修复保存与恢复；不以浏览器缓存替代 |
| 小样成功，实际素材量失败 | 内存、临时磁盘、输入规范化、FFmpeg 线程数和机器配置 | 优化后重测；若缩减承诺范围，同步[分阶段交付：MVP 必达，V2 增强表达，V3 扩展能力](product.md#s2)并明确记录，不能照旧宣称 MVP 达标 |

第 6 小时 A、B、C 都通过，才进入[AI 素材理解与选片测试：第 6–7 小时首测，第 14 小时前验证成片](ai-selection.md#s20-4)的 AI 选片首轮测试，再把主链路推进到 AI 自动编排。未通过就暂停 AI 接入和额外效果，先排查具体阻塞；备用方案见[发布类型的选择](deployment.md#s18-3)。

### 发布类型的选择

对于“HTTP 返回后还要继续跑 FFmpeg”的单实例原型，**优先评估 Replit Reserved VM**，它适合常驻 API 和后台任务。Autoscale 能缩到零并增加实例，需要额外处理任务生命周期、共享队列和跨实例状态；Static 无法执行这个 Python 后端。这个选择基于项目架构适配，不是平台性能实测。[Replit 部署类型](https://docs.replit.com/features/publishing/deployment-types)

前 2 小时确认账号可用的部署类型、CPU/内存和费用。如果资源不足，先检查串行执行、FFmpeg 线程数和素材规范化，必要时评估可承受的机器配置。缩小素材量或输出尺寸可用于定位瓶颈；若作为最终交付范围，需要同步[分阶段交付：MVP 必达，V2 增强表达，V3 扩展能力](product.md#s2)的承诺。仍无法上线时，用本地整套应用作为演示备用方案，保留 Replit 的开发与预览成果，并如实说明线上验证未通过；本地成功不能算完成“Replit 在线演示”验收。

开发预览和正式发布是两个环境。验证正式链接里的上传、生成、播放、下载与持久保存；代码修改后需要重新发布才影响线上版本。[发布说明](https://docs.replit.com/build/publish-your-app)
