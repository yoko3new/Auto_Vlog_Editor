## 当前成熟方案的比较与选择方法

以下依据 2026-10-09 查阅的官方文档和本项目约束提出。**没有用你们的素材运行横向实测，因此这是适配性评估，不是模型性能排行榜。** 比赛使用时锁定已经验证的具体模型 ID 和依赖版本。

<a id="s20-1"></a>

### 整体架构：推荐第一条

| 方案 | 主要价值 | 对本项目的代价 | 结论 |
| --- | --- | --- | --- |
| React + FastAPI + FFmpeg | 可定制页面；沿用 Python 分析库；明确控制剪辑和音频 | 需要对齐 HTTP 接口；视频动画要独立实现 | 本次主方案 |
| React + Remotion + Node 后端 | 用 React 组件描述视频排版与动画，适合模板化动态图形 | 增加视频合成学习、浏览器渲染环境与性能验证；现有 Python 分析还要衔接 | 当动态排版成为核心差异时再考虑 |
| Gradio + Python + FFmpeg | 页面与处理函数衔接快 | 自定义交互和视觉细节需要迁就组件 | 只有界面本身阻塞时才考虑应急，不用于掩盖渲染问题 |

Remotion 的服务端 `renderMedia()` 可把合成导出为视频，官方接口包含浏览器运行配置。它值得关注，但 React 网页并不能直接当作已经完成的视频模板；仍需定义逐帧动画、素材与音频安排。若以后采用，应先在目标机器跑出 10 秒样片并测资源，而不是比赛中途改写整套渲染器。[Remotion 渲染文档](https://www.remotion.dev/docs/renderer/render-media)

MVP 的 FFmpeg 只做硬切、静态标题、调色和固定 BGM。字幕属于 V2-3，溶解属于 V3-3。用真实封面和精确排版提高观感，复杂贴纸动画可以留到后续。

<a id="s20-2"></a>

### AI 理解与编排：按输入方式比较

| 候选 | 本项目可以怎么用 | 必须验证的部分 |
| --- | --- | --- |
| Claude 图像能力 + 结构化输出 | 带时间戳的关键帧、转录与元数据 → 内容描述、故事计划、修改操作 | 静态帧可能遗漏动作；检查镜头选择、重复与耗时 |
| OpenAI 图像能力 + 结构化输出 | 同一套关键帧和文本输入，保持输出契约一致 | 所选具体模型的图像/schema 支持、额度、响应时间 |
| Gemini 视频/图像理解 + 结构化输出 | 可以沿用关键帧，也可测试压缩视频输入理解连续事件 | 文件上传处理耗时、采样漏帧、时间边界与稳定性 |

能力依据：[Claude 视觉](https://platform.claude.com/docs/en/build-with-claude/vision)与[结构化输出](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)；[OpenAI 视觉](https://developers.openai.com/api/docs/guides/images-vision)与[结构化输出](https://developers.openai.com/api/docs/guides/structured-outputs)；[Gemini 视频理解](https://ai.google.dev/gemini-api/docs/video-understanding)与[结构化输出](https://ai.google.dev/gemini-api/docs/structured-output)。

项目尚无已接入的 API，没有迁移成本前提。先用手头已开通、额度可用的一家跑通；再最多选另一家比较。原草案提到 Claude，不代表已经证明它的剪辑审美领先。连续动作确实影响选片时，Gemini 的原生视频输入值得测；它也不保证逐帧精确定位。

保留三个函数就够：`analyze_clips()`、`make_edit_plan()`、`parse_edit_request()`。默认由同一供应商完成；不要为展示架构堆叠多 Agent、LangChain、向量数据库或模型路由系统。关键是稳定的素材 ID、时间戳和业务校验。

这里讨论的是应用运行时的 AI 编排。开发阶段可以使用多个编码助手，但个人工具与调度方式不构成产品运行依赖。

### V2-3 语音选型：识别准与字幕对齐是两个要求

| 候选 | 适用情况 | 本项目注意点 |
| --- | --- | --- |
| OpenAI Whisper API（`whisper-1`） | 希望云端返回词或片段时间戳 | 时间戳能力要按接口选，不能假定所有更新的转录模型都返回逐词时间 |
| ElevenLabs Scribe | 希望云端转录并提供词级时间信息 | 用实际中英混合口播验证准确率、边界、耗时和费用 |
| faster-whisper | 本地已有可用环境，或希望不依赖转录 API | CPU 速度与模型大小需要实测；Replit 环境不默认有 CUDA GPU |

依据：[OpenAI 时间戳说明](https://developers.openai.com/api/docs/guides/speech-to-text#timestamps)、[ElevenLabs 转录文档](https://elevenlabs.io/docs/overview/capabilities/speech-to-text)、[faster-whisper 仓库](https://github.com/SYSTRAN/faster-whisper)。

MVP 跳过本节，不需要语音服务密钥。进入 V2-3 后，在 Replit 上先尝试云端转录，以免转录和渲染争抢有限 CPU；如果本地方案已经稳定且够快，则保留。只实现一个转录适配器。没有口播的素材跳过 ASR；转录失败可退到纯画面 + BGM，并明确提示。

ElevenLabs 配音属于 V3-4，不是 V2-3 转录的必需依赖。MVP 只有 BGM，V2-3 优先保留真实短口播；之后若旁白确实有益，才加用户确认文字的一句旁白，测得真实音频时长后放入时间线。

### AI 素材理解与选片测试：第 6–7 小时首测，第 14 小时前验证成片

**目的：验证“抽取的画面是否足以找到精彩瞬间，以及 AI 能否选出适合校园 vlog 开场速剪的片段”。** 这是 MVP 的小样本工程筛选，不是模型排行榜。当前状态为**未执行**；没有选定已验证的具体模型，也没有真实成绩或费用记录。

时间安排：[开工验证：先确认 Replit 能跑通，再接 AI](deployment.md#s18-2) Replit A、B、C 通过后，在第 6–7 小时完成首轮测试，控制在一小时内；第 7–14 小时接通编译与渲染，确认最终视频仍保留关键瞬间；第 14–24 小时用第二套素材复查。它属于原有 AI 开发预算，不额外增加阶段。修改指令测试仍在第 14–24 小时 MVP 验收中完成，口播和转录留到 V2-3。

**第一步：准备 10 段素材，并先写下人的判断**

从 Replit 实际负载测试的 10–15 段素材中选 10 段，覆盖上课、走路、吃饭、自习或朋友互动等校园场景。其中包含一组内容相近的镜头、一个短暂动作、一段有意义但角度欠佳或轻微晃动的画面，以及一个明显误拍区间。这些情况可以出现在同一段素材里。

由你先看片并标注，队友复核。在看模型输出前写好，避免事后迁就模型答案。开发时可保存为独立评估表，不改动[JSON 数据契约：MVP 可用，V2/V3 可扩展](reference/timeline.md#s6)的产品 JSON 契约：

| 人工标注字段 | 要写什么 |
| --- | --- |
| `clip_id` | 与真实素材登记一致 |
| 内容事实 | 画面里实际发生了什么，不猜人物身份、地点或心情 |
| 关键瞬间 | 在整个测试集中选 3 个应当保留、可在 MVP 镜头时长内看清的瞬间；记录原素材中的起止秒数和理由 |
| 重复组 | 哪几段表达相同内容，保留一段即可；同一文件的不同内容不能仅因 ID 相同就判重复 |
| 不可用区间 | 明显误拍、严重遮挡或无法辨认的区间 |
| 画质与内容取舍 | 哪些片段虽有轻微晃动或角度问题，仍值得保留 |

人工标注仅用于评估，不作为答案发送给模型。初始 10 段可先测试理解和选片；如果剔除重复、误拍后不足以构成 30 秒，正确结果是报告素材不足。渲染验收时补回主素材集中的其他有效素材，总数仍控制在 10–15 段，不靠重复片段凑长度。

**第二步：固定输入，先跑一家模型**

每段先抽约 3 张低分辨率代表画面，附 `clip_id`、原素材时间戳、时长和方向；记录实际帧数、尺寸和采样规则。模型先给出内容分析，再按[`edit_plan.json`：AI 输出什么](reference/timeline.md#s6-5)返回剪辑计划，后端负责补外层标识、校验和编译。明确任务是约 30 秒开场速剪，优先代表性瞬间、活动差异和自然感。

先用已开通且额度可用的一家跑通。同一配置至少调用两次，观察是否稳定，不能复用上次模型回答当作第二次测试。首轮最多比较另一家；对比时保持素材、抽帧、提示词目标和输出契约相同。更换采样或改用视频输入属于另一套输入方案，单独记录，不能把效果差异都归因于模型。

**第三步：对照标注，并检查真正截取到的画面**

| 检查项 | 怎么评估 | 本次建议放行标准 |
| --- | --- | --- |
| 内容理解 | 人工逐项核对主体与活动，记录正确项数 / 总项数及具体误判 | 没有影响选片的重要事实错误；不编造具体身份、日期、地点或个人感受 |
| 关键瞬间 | 对照预先选定的 3 个瞬间；记录命中数 / 3 | 两次计划都保留这 3 个瞬间；第 14 小时前在最终 MP4 中也能看清核心动作或画面 |
| 重复与不可用内容 | 检查重复组是否挤占多个镜头，误拍区间是否入选 | 不用明显重复内容凑时长，不选已标注的不可用区间 |
| 保留原生感 | 核对标注为有价值但画质不完美的素材 | 不仅因为轻微晃动、普通角度或昏暗就把有意义的内容全部排除 |
| 时间与契约 | 校验真实素材 ID、候选范围、建议时长和最终时间线 | 进入渲染的计划没有越界或无效引用；原始失败和修复次数另记，不能静默写成模型一次成功 |
| 速剪效果 | 实际看成片的开头、片段衔接、标题与 BGM | 能表达校园日常主题，标题有依据，主要画面看得清；两人指出的具体问题有记录 |
| 耗时与费用 | 分开记录抽帧、分析、规划、校验重试、渲染和保存 | 有实际记录；未取得用量或账单时标为未采集，不编造费用；90 秒仍不是放行门槛 |

这里的标准是本项目的小样本验收建议，不代表对所有用户素材的准确率承诺。不要只检查宽泛的 `source_window` 是否覆盖关键瞬间：编译器可能从中截出别的位置，必须查看最终选中的区间和实际 MP4。第 6–7 小时尚未渲染的项目标为“待成片复核”，不能提前判为全部通过。

**失败时按原因修复，再复测**

- 关键瞬间没有出现在输入画面中：优先在该类片段增加采样，记录新的采样策略；不要仅靠换模型期待它猜中。策略修订后也在第二套素材验证。
- 画面已经包含瞬间，但模型理解错误或忽略：先调整任务描述和选片优先级，仍不理想时才比较另一家。连续动作仍无法判断时，可在同一预算内另测短视频输入方案；保持独立结果记录。
- 内容理解正确，但最终截取错过瞬间：检查候选范围和编译器截取逻辑；不把后端时间计算错误算成模型审美问题。
- 输出格式或接口失败：检查服务支持的 schema、输入限制和超时，保留原始错误及有限重试记录。规则降级可以用于应急，但不能计入 AI 测试通过。

首轮一小时结束后停止扩展候选名单，选择已经可用的一家继续集成；若没有一家通过，就记录具体阻塞并在第 7–14 小时修复主链路，不填“已选定”。未通过第 14 小时关卡时按[36 小时时间表与阶段关卡](collaboration.md#s14)收缩工作。

开发时将素材清单、人工标注、抽帧配置、提示词版本、具体模型 ID、原始回答、校验结果、每次用量和耗时，以及最终成片引用集中存入 `fixtures/ai-selection/`；这是待开发的记录目录，目前尚未生成测试结果。第 14–24 小时使用未参与首轮调参的第二套素材再验收，完成后锁定主模型和配置。
